# v0.8 语料扩充与规模化评估

> 一句话：把语料从 120 份扩到 **869 份**研报（向量块 11,823 → **82,981**，7×），重跑 RAGAS 证明"更多语料 → 更好检索"——完整链路 ContextPrecision 0.726→**0.822**、Faithfulness 0.847→**0.923**；期间把规模化才会暴露的工程脆弱点（VL 挂起、长任务被杀、内容审核、评估多轮串台）逐一修掉。

## 为什么这一期重要

三件事一次性验证：
1. **管道的可扩展性不是嘴上说的**——前面几期反复强调"增量入库、断点续跑、抽象层",这一期 7 倍数据灌进去,上层零改动、已处理内容零重编,把设计兑现了。
2. **用数字证明数据的价值**——作品集里"我扩了库"是苦劳,"扩库后检索精度 +0.096、忠实度 +0.076"是功劳。
3. **规模化会逼出隐藏 bug**——120 份时跑得好好的代码,869 份时把外部 API、长任务、Windows 编码、有状态评估的脆弱点全抖了出来。

## 技术要点

### 1. 增量入库兑现：只算新增，旧的全跳过

| 阶段 | 幂等键 | 行为 |
|---|---|---|
| parse_pdfs | 文件内容 MD5 | 同内容（即便改名）只解析一次 |
| build_index | `indexed.json` 记 digest | 11,823 块不重编，只编新增 749 份 |
| parse_charts | `(digest, page)` | 已转写的页跳过 |
| BM25 / 图注向量 | 检测 `len(cache) != len(metas)` | 规模变了**自动重建**，无需手动 |

最终 82,981 块里,旧的 11,823 块一块没重新编码。

### 2. 体检先行：869 份不是直接灌

灌库前先扫一遍,避免脏数据进库:
- **文件名冲突检测**（最关键）：来源标识 = 文件名,裁图端点也靠文件名找 PDF。重名会导致来源串台 / 复制时互相覆盖。实测：组内 0 重名,与现有 42 个重名且**内容相同**(安全)。
- **内容哈希去重**：组内 37 份、与现有 42 份完全相同 → 自动跳过。
- 净新增 **749 份**,0 损坏。

## 踩坑（规模化的现实，全是面试料）

1. **VL 接口无超时 → 挂起请求堵死整条管道**
   反复"卡住几分钟不动",根因是 OpenAI 客户端**默认无超时**,一个挂起的请求能阻塞到 10 分钟。修复：`OpenAI(timeout=90, max_retries=2)`,挂起快速失败、交给重试循环兜底。

2. **长任务被环境周期性杀掉 → 断点续跑兜底**
   这台 Windows 机器每隔几分钟会杀掉长跑的后台 python(进程直接消失、无异常)。因为全链路幂等,**每次重启都从断点续上,1482 页转写零数据丢失**。收尾阶段改用前台跑,绕开后台回收。
   *教训：不稳定环境里,"可断点续跑"不是锦上添花,是保命设计。*

3. **一页触发百炼内容审核（`data_inspection_failed`）**
   某页图片被内容安全拦截,重试 3 次全 400。脚本捕获后记失败、跳过——1482 页里仅此 1 页,无害。这也是"反复卡住"的真凶之一。

4. **Windows GBK stdout 崩溃**
   某文件名含 `Ü`(U+00DC),`print` 到重定向文件时 GBK 编码报错直接终止脚本。修复：`PYTHONUTF8=1` 强制 UTF-8 输出。

5. **评估的多轮串台 bug（v0.7 引入的副作用）**
   `collect.py` 对 16 道题共用 `thread_id="default"`,而 v0.7 的 checkpointer 会按 thread 累积历史 → 第 2 题的 condense 看到第 1 题历史、把无关问题"改写"歪了。修复：**每题独立 `thread_id`**。
   *教训：给系统加了状态(多轮记忆),所有"批量/评估"入口都要显式隔离会话,否则状态会悄悄污染结果。*

## 实测：扩库前后（完整链路，RAGAS 16 题，DeepSeek 裁判）

| 指标 | 120 份 | 869 份 | Δ |
|---|---|---|---|
| ContextPrecision | 0.726 | **0.822** | +0.096 |
| Faithfulness | 0.847 | **0.923** | +0.076 |
| AnswerRelevancy | 0.890 | **0.904** | +0.014 |

相对基线的增益也全线转正(基线 vs 链路,869 份)：ContextPrecision +0.146、AnswerRelevancy +0.121、Faithfulness **+0.042**。

**最值得说的归因**：v0.4 时完整链路 Faithfulness 比基线**低 0.034**(当时诚实记录的 trade-off：小语料下上下文不足,精排反而筛掉了部分可支撑的内容)。扩库后证据更充分,这个负 trade-off **翻正为 +0.042**——数据规模直接改善了忠实度。

## 面试高频问题

**Q: 7 倍语料,检索和部署扛得住吗？**
A: FAISS 8 万块仍是毫秒级、索引约 340MB;真正的内存大头是 BM25 常驻语料(~1G)和两个本地模型(~4.6G)。CPU 部署 8G 偏紧、16G 宽松;图片/图表是按需渲染,不占常驻内存。详见部署相关讨论。

**Q: 为什么扩库后忠实度反而升了，甚至翻正？**
A: 忠实度衡量"答案论断能否被检索上下文支撑"。小语料时,精排后剩下的优质上下文偏少,模型容易"超出上下文发挥"→ 扣分;语料厚了,同一问题能召回更充分、更对口的证据,答案有据可依,忠实度自然上去。这说明**检索质量是生成忠实度的上游**。

**Q: 长任务在会杀进程的环境里怎么保证不白跑？**
A: 全链路幂等 + 逐单元落盘 + 断点续跑:parse 按 (哈希,页) 落盘、build_index 按 doc 记 indexed、每步 flush。进程被杀后重启秒级续上,1482 页 VL 调用零重复、零丢失。

**Q: 那个评估多轮 bug 暴露了什么工程问题？**
A: 一旦系统变"有状态"(多轮记忆),评估/批处理这类"伪并发"入口必须显式隔离会话(独立 thread_id),否则上一条的状态会污染下一条——这是有状态 Agent 做离线评估时极易踩的坑。
