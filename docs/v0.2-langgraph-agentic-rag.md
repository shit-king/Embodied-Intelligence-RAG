# v0.2 LangGraph Agentic RAG

> 一句话：把"一次检索一次生成"的线性 RAG 升级为**会做决策的检索流程**——简单问题直通，复杂问题拆解多路检索，检索质量差自动改写重试，每步决策实时推送前端。

## 为什么需要 Agentic

v0.1 的单轮 RAG 有一个结构性缺陷：**用户问题 ≠ 好的检索查询**。

- "对比不同报告对市场规模的预测差异"——这一句话做向量检索，召回的是"泛泛谈市场规模"的块，而"对比"需要的是**多个独立来源各自的预测数据**
- 复合问题（"X的现状、瓶颈和趋势"）一次检索 top-k 无法同时覆盖三个子主题
- 查询用词与报告用词不匹配时（口语 vs 行业黑话），检索质量差但系统毫无察觉，照样拿垃圾上下文生成

解法：在检索前后加**决策节点**——这就是 Agentic RAG，本质是把"检索"从一个函数调用变成一个有分支和循环的流程。

## 图设计

```
START → route ──简单──→ retrieve ──充分──→ synthesize → END
           └──复杂──→ decompose ──┘   └─不足且未重试─→ rewrite ─→ retrieve（重试一次）
```

五个节点，各自职责单一：

| 节点 | 职责 | LLM调用 |
|---|---|---|
| route | 判断 simple/complex | 是（JSON mode） |
| decompose | 复杂问题拆为2-4个自包含子查询 | 是（JSON mode） |
| retrieve | （多）查询检索、跨查询合并去重 | 否 |
| rewrite | 检索失败时改写查询（换行业表述/补同义词） | 是（JSON mode） |
| synthesize | 按引用Prompt合成最终回答 | 是（流式） |

实测路由效果：
- "智元机器人是做什么的？" → simple，直接检索
- "对比不同报告对人形机器人量产时间表的预测，并分析数据瓶颈的影响" → complex，拆为"量产时间表预测 对比"和"数据瓶颈 量产 影响"两路

## 核心技术点

### 1. LangGraph 的三个核心概念

```python
class AgentState(TypedDict, total=False):
    question: str
    route: str
    sub_queries: list[str]
    hits: list[dict]
    retried: bool
    answer: str
```

- **State**：TypedDict 定义的共享状态，节点函数**返回增量 delta**（如 `{"route": "complex"}`），LangGraph 负责合并进全局状态——节点之间不直接传参，全靠状态总线
- **条件边**：`add_conditional_edges("route", after_route, [...])`，路由函数读状态返回下一个节点名，**分支逻辑是普通 Python 函数**，完全可测试
- **循环**：`rewrite → retrieve` 形成环。**防死循环**靠状态里的 `retried` 标志：`after_retrieve` 发现已重试过就强制走 synthesize。面试必问"agent 怎么防止无限循环"，答案就是在状态里记录尝试次数+条件边硬性出口

### 2. 为什么用图编排而不是 ReAct 自由 agent

这是个重要的架构决策，面试可以主动讲：

- **可控性**：图结构固定，最坏情况就是"路由→拆解→检索→重试→合成"，延迟和成本有上界；ReAct 让 LLM 自由决定调用什么工具，可能反复检索十几次
- **可调试**：每个节点输入输出明确，问题能定位到具体节点；自由 agent 的失败是黑盒
- **够用**：知识库问答的决策空间就这几种（拆不拆、重不重试），不需要开放式规划

结论：**决策点有限的场景用显式图，开放式任务才考虑自由 agent**。

### 3. DeepSeek JSON mode 结构化输出

route/decompose/rewrite 的输出必须可程序解析：

```python
llm.bind(response_format={"type": "json_object"})
```

配合三层防御：prompt 里写明 JSON schema 和示例 → `json.loads` 包 try/except 返回空 dict → 下游对空值有默认行为（路由默认 simple、拆解为空则用原问题）。**LLM 的结构化输出永远要按"可能失败"设计降级路径**。

### 4. 双通道流式：updates + messages

这是 LangGraph 集成里最值得讲的细节。前端要同时拿到两类信息：

- **agent 步骤事件**（路由结果、子查询列表、重试提示）→ `stream_mode="updates"`：每个节点执行完产出状态增量
- **最终回答的 token 流** → `stream_mode="messages"`：LangGraph 通过 callback 捕获**节点内部** LLM 调用的逐 token 输出

```python
for mode, chunk in graph.stream({"question": q}, stream_mode=["updates", "messages"]):
    if mode == "messages":
        msg, meta = chunk
        if meta.get("langgraph_node") == "synthesize":  # 只放行合成节点的token
            yield token
    elif mode == "updates":
        ...  # 节点名→翻译成用户可读的step事件
```

**关键过滤**：route/decompose 节点也在调 LLM，不过滤 `langgraph_node` 的话，路由的 JSON 输出会混进用户看到的回答里。

### 5. SSE 事件协议升级

```
event: step      data: "路由判断：复杂问题，需拆解检索"
event: step      data: "拆解为3个子查询：……"
event: step      data: "召回6个相关片段"
event: sources   data: [{source, page, text, score}, ...]
data: "根"  data: "据"  ...        ← 默认message事件=token
event: done
```

前端把 step 渲染成回答气泡上方的灰色步骤行——**agent 的思考过程可视化**，既是产品体验（用户知道系统在干什么），也是 demo 时的视觉亮点。

### 6. 多查询合并去重

子查询各自召回后合并，去重 key 用 `(source, page, text[:80])`——不同子查询经常命中同一块（比如都命中某份报告的核心页），不去重会浪费宝贵的上下文窗口。

## 面试高频问题

**Q: LangGraph 和 LangChain 的 Chain 有什么本质区别？**
A: Chain 是 DAG（有向无环），数据单向流过；LangGraph 是**带状态的有向图，允许环**——循环（重试、迭代优化）必须用图。状态合并机制也不同：Chain 靠输入输出传递，Graph 靠共享 State + 增量合并。

**Q: 拆解出的子查询质量差怎么办？**
A: 三道防线：prompt 约束（自包含、单主题、保留实体名）；解析失败降级用原问题检索；最终还有 rerank 兜底过滤无关召回（v0.3）。另外子查询上限4个，控制成本和噪声。

**Q: 这个 agent 的延迟构成？**
A: 简单路径 = 路由(1次小LLM调用) + 检索 + 合成；复杂路径多一次拆解调用。路由/拆解输出都很短（几十token），延迟主要在合成。相比纯 RAG 增加约1-2秒，换来复杂问题质量的明显提升——并且步骤实时推送让等待"有内容看"，体感延迟更低。

**Q: 状态里为什么不放对话历史？**
A: 当前是单轮设计。LangGraph 加多轮记忆的标准做法是 checkpointer（按 thread_id 持久化状态），是下一步迭代方向。
