# v0.4 RAGAS 评估体系

> 一句话：把"肉眼觉得变好了"变成**可量化、可复现的数字**——16题评估集，v0.1基线 vs v0.3完整链路双跑，RAGAS 三指标用 DeepSeek 当裁判打分，输出含诚实 trade-off 分析的对比报告。

## 为什么 RAG 必须做评估

- RAG 链路参数极多（chunk大小、top-k、融合权重、rerank阈值……），没有评估就只能拍脑袋调参
- "演示时效果不错"≠"系统性变好"——单个case的改善可能伴随其他case的回退（本次评估恰好抓到了一个）
- 面试视角：能讲出"我的优化带来 ContextPrecision +0.255"和只能说"感觉准了很多"，是两个层次

## 评估设计

### 数据集：16题 × 4类

| 类别 | 设计意图 | 例 |
|---|---|---|
| 事实查询 | 基础能力 | 具身智能的定义是什么 |
| 专有名词 | 考BM25混合检索 | Unitree Dex5灵巧手有什么特点 |
| 数字事实 | 考rerank找含数字的页 | 关节占制造成本的比例 |
| 跨文档综合 | 考agent拆解 | 对比不同报告的量产时间表预测 |

**分类设计是为了归因**：每类对应一个被测机制，总分变化能定位到"哪个机制带来的"。

### 三个指标（全部免人工标注）

| 指标 | 测什么 | 怎么算 |
|---|---|---|
| Faithfulness | 回答是否忠实于上下文（反幻觉） | 裁判把回答拆成原子论断，逐条判断能否被检索上下文支持 |
| AnswerRelevancy | 回答是否切题 | 裁判从回答反推问题，与原问题算 embedding 相似度 |
| ContextPrecision | 检索的上下文干不干净 | 裁判逐条判断每个上下文块与问题的相关性，按排序加权 |

选择"无参考"变体（不需要人工写标准答案）是冷启动期的务实取舍；代价是测不了 context_recall（漏检率）。

### 双配置对照

同一批问题分别跑 v0.1（纯向量 top6 + 直接生成）和 v0.3（路由/拆解 + 混合召回 + rerank + 合成），**指标差值直接归因于三期的全部改动**。

## 架构：采集与打分解耦

```
主venv（业务栈 langchain 1.x）          eval venv（ragas + langchain-community 0.3）
┌──────────────────────┐   JSONL    ┌──────────────────────────┐
│ collect.py 跑两套链路 │ ─────────→ │ score.py RAGAS+DeepSeek裁判 │ → results.md
└──────────────────────┘  (文件接口)  └──────────────────────────┘
```

为什么解耦：ragas 0.4.3 import 了 `langchain_community.chat_models.vertexai`——这个模块在新版 community 中已被移除，与主环境的 langchain 1.x 栈**导入即崩**。两个 venv 以 JSONL 文件为接口，互不污染。

附带收益：采集结果落盘后可以反复用不同指标/裁判重打分，不用重跑昂贵的pipeline；采集脚本带断点续跑。

## 踩坑记录（评估工程的真实面貌）

| 坑 | 现象 | 解决 |
|---|---|---|
| ragas与langchain 1.x冲突 | import即ModuleNotFoundError | 独立eval venv + 文件接口解耦 |
| 裁判调用超时 | agent链路10块上下文→ContextPrecision调用量大，13/16样本NaN | `RunConfig(timeout=600, max_retries=15, max_workers=4)` |
| DeepSeek不支持n>1 | AnswerRelevancy默认一次生成3个反推问题（n=3），400报错 | `ResponseRelevancy(strictness=1)` |
| NaN污染均值 | 失败样本静默变NaN，表格出现+nan | 打分后显式检查NaN计数，不为0不出报告 |

**教训**：LLM-as-judge 的评估管道本身就是个分布式调用系统，超时/限流/格式解析失败都会静默产生缺失值——**出报告前必须检查数据完整性**，否则均值是假的。

## 结果与解读（v0.1 → v0.3）

| 指标 | 基线 | 完整链路 | Δ |
|---|---|---|---|
| Faithfulness | 0.880 | 0.847 | **-0.034** |
| AnswerRelevancy | 0.841 | 0.890 | +0.049 |
| ContextPrecision | 0.678 | 0.726 | +0.048 |

- **最大单项**：数字事实类 ContextPrecision +0.255（rerank把含数字的页排进上下文），与 v0.3 的检索实验互相印证
- **跨文档综合 Faithfulness +0.122**：拆解让复杂问题有了对口证据
- **诚实的trade-off**：总体 Faithfulness 微降——agent 回答更长、论断更多，每个论断都是被扣分的机会；跨块归纳的合理推断也被严格判为"无直接支持"。这不是bug，是"综合能力 vs 严格忠实度"的真实张力，改进方向是约束数字类回答不做跨来源推算

## 面试高频问题

**Q: 没有标注数据怎么评估RAG？**
A: 用无参考指标三件套（faithfulness/answer_relevancy/context_precision），LLM当裁判，零标注冷启动。代价是测不了召回漏检，长期还是要建带golden answer的评估集补context_recall。

**Q: LLM裁判可信吗？**
A: 有噪声但方向可信。控制手段：裁判temperature=0、关注差值而非绝对值、样本量摊薄单题噪声、关键结论人工抽检。我的报告里明确写了"结论看方向而非精确差值"——知道评估的边界本身就是评估能力的一部分。

**Q: 你的优化让指标下降了怎么办？**
A: （这是个展示成熟度的机会）先归因再决策：Faithfulness下降集中在数字类，原因是回答变长论断变多+跨块归纳被严判。判断这是可接受的trade-off（换来了相关性和检索精度提升），同时给出针对性缓解方案（数字原样引用约束）。**评估的价值就是把模糊的"变好了吗"变成具体的工程决策**。

**Q: 为什么对照实验有说服力？**
A: 同一评估集、同一裁判、同一时间窗双跑，唯一变量是链路版本——差值可归因。如果只跑新版本看绝对分，0.89是高是低根本无从判断。
