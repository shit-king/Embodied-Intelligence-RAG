# v0.1 MVP：RAG 基础链路

> 一句话：把 120 份行业报告 PDF 变成一个"回答必带报告名+页码引用"的问答系统，跑通 **解析 → 切块 → 向量化 → 检索 → 生成 → 流式界面** 全链路。

## 这一版做了什么

| 环节 | 实现 | 产出 |
|---|---|---|
| PDF解析 | PyMuPDF 按页提取 | 120份文档（去重后）→ 4,765 文本页 |
| 切块 | 中文递归切块 500字/重叠100 | 10,933 个文本块 |
| 向量化 | bge-m3 本地GPU编码 | 1024维归一化向量 |
| 存储 | FAISS（内积索引） | data/faiss/ |
| 生成 | DeepSeek + 强制引用Prompt | 带 [来源N] 的回答 |
| 服务 | FastAPI SSE + 单页前端 | 流式问答 + 来源卡片 |

## 核心技术点

### 1. 按页解析：引用溯源的设计起点

整个系统"回答可溯源到第几页"的能力，是在**解析阶段**就决定的——`parse_pdfs.py` 按页提取文本，每页记录页码；切块时块继承 `{source: 报告名, page: 页码}` 元数据；检索命中后元数据随块返回；生成时拼进上下文标头 `【来源N】《报告名》第X页`。

**要点**：溯源不是生成阶段"加个prompt"能解决的，元数据必须从数据管道源头一路携带到底。

工程细节：
- **内容哈希去重**：对文件字节算 MD5，同一份报告的多个重名副本只解析一次（123个文件去重为120份）
- **断点续跑**：每解析完一份就写 `manifest.json`，中断后重跑自动跳过已完成的
- **扫描页检测**：页文本 <20 字符视为扫描图/纯图表页，记录页码跳过（280页，留给多模态版本处理），而不是混入空文本污染索引

### 2. 中文切块：分隔符优先级

```python
RecursiveCharacterTextSplitter(
    chunk_size=500, chunk_overlap=100,
    separators=["\n\n", "\n", "。", "！", "？", "；", "，", " ", ""],
)
```

- 递归切块的逻辑：优先在段落边界切，切不下去才降级到句号、再到逗号——尽量保住语义完整的单元
- **默认分隔符不适合中文**（只有 `\n` 和空格），必须显式加中文标点
- 500字：太小则上下文碎片化（一个论点被切断），太大则检索粒度粗、上下文塞入无关内容。行业报告以"段落+数据"为主，500字约2-4个段落
- 重叠100：防止关键句恰好被边界切断，代价是约20%存储冗余

### 3. Embedding：bge-m3 与余弦相似度

- **选型理由**：中文检索效果第一梯队（C-MTEB榜）、支持多语言、本地推理零API成本
- `normalize_embeddings=True` + FAISS `IndexFlatIP`（内积）：**归一化后向量的内积 = 余弦相似度**，这是"为什么内积索引能当余弦用"的标准答案
- `max_seq_length=512`：块只有500字，没必要用默认8192的长度配置（显存和速度都浪费）
- `@lru_cache` 单例加载：模型2.3GB，绝不能每次请求重新加载

### 4. 向量库：抽象层 + FAISS 实战细节

定义了 `VectorStore` 抽象基类（`add/search/count`），底层实现可换。这个设计当天就赚回了成本：Chroma 在目标环境不可用，**切换到 FAISS 只改了一个文件，上层检索/生成代码零改动**。

FAISS 细节：
- 1万级数据用 `IndexFlatIP`（精确暴力检索）而不是 IVF/HNSW：毫秒级返回且100%精确，**近似索引是百万级以上才需要的优化**——按数据规模选索引是面试常考点
- FAISS 的 C++ 层不支持 Windows 中文路径，用 `faiss.serialize_index()` 转字节流后由 Python 写文件绕过
- 元数据存 JSONL 旁路文件，行号与向量插入顺序对齐

### 5. 生成：用 Prompt 约束幻觉

System prompt 的四条核心约束：
1. 只依据提供的资料回答，**没有的信息明确说"资料中未提及"**（给模型一个"不知道"的出口，比单纯禁止编造有效）
2. 句末标注 `[来源N]`
3. 数据（市场规模/增速/融资额）**必须**带来源
4. 多份报告口径不一致时分别列出（实测有效：模型会主动区分"全球192亿 vs 中国4853亿"两个口径）

`temperature=0.3`：事实问答要低温度，但不为0以保留组织语言的流畅度。

### 6. SSE 流式接口

事件协议设计：先推 `sources`（检索结果，前端立即渲染来源卡片），再流式推 token，最后 `done`。**来源先行**让用户在等待生成时就能看到"系统找到了什么"。

前端用 `fetch` + `ReadableStream` 手动解析 SSE（原生 `EventSource` 不支持 POST），按 `\n\n` 分帧、`event:`/`data:` 解析。

## 真实踩坑（面试讲"工程能力"的素材）

| 坑 | 现象 | 解决 |
|---|---|---|
| chromadb 1.x | 写入正常，**进程重启后** count/query 全部报 HNSW 加载错误 | 验证中英文路径都复现 → 判定 Rust 内核 bug → 降级 0.6.3 又因 cp313 无 wheel 失败 → 靠抽象层切 FAISS |
| U+2028 分隔符 | JSONL 读取报 "Unterminated string" | PDF 文本含 Unicode 行分隔符，`splitlines()` 会按它切行把一条 JSON 拆成两半；改用文件行迭代（只按 \n） |
| 旧显卡驱动 | torch cu126 报 "driver too old" | 驱动只支持 CUDA 11.6 → 换 cu118 构建（CUDA 11 系列向下兼容驱动） |
| 大文件断点 | torch 2.6GB 下载中断 | pip 25.1+ 的 `--resume-retries` 断点续传 |

## 面试高频问题

**Q: chunk 大小怎么定的？**
A: 没有银弹，按语料特征定。行业报告段落密度高、一个论点2-4段，500字能装下完整论点；重叠100防边界切断。验证方式是抽查检索结果是否"答案被切一半"。（加分：提到后续可用评估集量化调参）

**Q: 如何减少 RAG 幻觉？**
A: 三层：检索层保证上下文质量（后续版本的混合检索+rerank）；Prompt 层给"不知道"的出口+强制引用；展示层让用户可一键核对原文（引用卡片）。引用本身就是对模型的约束——要标注来源就必须基于来源写。

**Q: 为什么用 FAISS 不用 Milvus？**
A: 1万级数据、单机单用户场景，FAISS 精确检索毫秒级返回，引入 Milvus 是过度设计。但通过 VectorStore 抽象层保留了迁移路径——数据规模上去（百万级）或需要标量过滤、多副本时再迁。技术选型要匹配数据规模和场景，不是越重越好。

**Q: 向量归一化后内积为什么等于余弦？**
A: cos(a,b) = a·b / (|a||b|)，归一化后分母为1。所以 IndexFlatIP 配归一化向量就是余弦检索。
