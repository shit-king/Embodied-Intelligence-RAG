# v0.3 混合检索 + Rerank 精排

> 一句话：单路向量检索升级为**召回-精排两阶段架构**——向量+BM25双路宽召回，RRF融合，交叉编码器精排，rerank分数还复用为"检索失败"的判据。

## 为什么向量检索不够

向量检索的弱点是有规律的，实测三类典型 case：

| 查询类型 | 例子 | 纯向量的问题 |
|---|---|---|
| 专有名词/型号 | "Unitree Dex5" | embedding 对没见过的型号词不敏感，top3混入无关的汽车产业链报告 |
| 缩写/术语 | "PEEK材料" | 字面精确匹配才是强信号，语义模型反而"联想"过头 |
| 数字事实 | "关节占制造成本比例" | 命中"泛泛谈成本"的块，错过含"60%~70%"具体数字的页 |

BM25 恰好相反：**精确词匹配极强，语义泛化为零**。两者互补，这就是混合检索的动机。

## 两阶段架构

```
查询 ──→ 向量召回 top15 ──┐
                          ├─ RRF融合 ─→ 去重合并(≤30) ─→ bge-reranker精排 ─→ top10 进生成
     └─→ BM25召回 top15 ──┘
```

设计原则：**召回阶段要快、要宽（宁多勿漏），精排阶段要准、要窄**。这是搜索/推荐系统的经典分层，迁移到 RAG 同样适用。

## 核心技术点

### 1. BM25：jieba 分词 + 同源语料

```python
def _tokenize(text):
    return [t for t in jieba.cut_for_search(text) if t.strip()]
```

- `cut_for_search` 模式：在精确切分基础上对长词再切（"人形机器人"→ 同时出"人形机器人/人形/机器人"），提高召回
- **语料对齐**：BM25 直接基于 FAISS 同一份 `meta.jsonl` 构建，两路召回的结果天然是同一套块对象，融合去重无需映射
- 1万块的分词结果 pickle 缓存，缓存长度与语料不一致时自动重建（防新增文档后索引漂移）

### 2. RRF 融合：为什么不用加权分数

两路的分数体系完全不可比：余弦 0~1，BM25 0~20+ 无上界。直接加权需要归一化，而归一化系数依赖语料分布，难调且脆弱。

RRF（Reciprocal Rank Fusion）只看**排名**不看分数：

```
score(d) = Σ_路 1 / (k + rank_d)    k=60
```

- 在两路都排前列的文档得分最高；只在单路出现的也有机会
- k=60 是论文默认值，作用是平滑头部差距（rank1 和 rank3 不至于差太多）
- **一行公式消掉整个归一化问题**，这是它成为工业界默认融合方法的原因

### 3. 交叉编码器精排：和双塔的本质区别

| | 双塔（bge-m3） | 交叉编码（bge-reranker-v2-m3） |
|---|---|---|
| 计算方式 | 查询、文档**分别**编码成向量，算余弦 | 查询+文档**拼接**后整体过模型，输出相关分 |
| 交互深度 | 只在最后一步点积交互 | 每层 attention 都在做词级交互 |
| 速度 | 文档向量可预计算，检索O(1)次编码 | 每个候选都要过一次模型，无法预计算 |
| 用法 | 召回（万级候选里挑几十） | 精排（几十个候选里挑前10） |

**为什么准**：双塔模型必须把整段文本压缩成单个向量，细粒度信息（具体型号、数字）有损；交叉编码器能看到"查询的'Dex5'和文档的'Dex5'是同一个词"这种词级证据。

实测：候选30个、batch 8，GTX 1660 SUPER 上精排约1秒。**精排延迟与候选数线性相关**，所以候选上限（30）是质量-延迟的直接调节旋钮。

### 4. rerank 分数的复用：检索质量判据

v0.2 用"余弦最高分<0.5"判断检索失败触发查询改写，但余弦分数区分度差（好坏结果都挤在0.6-0.8）。交叉编码器的 sigmoid 分数判别性强得多：相关结果0.9+，无关结果0.0x，拉开两个数量级。

所以 v0.3 把改写重试的判据改成 **rerank 最高分 < 0.2**——一个组件同时服务排序和质量监控，没有额外成本。

### 5. 显存预算

6GB 显卡同时容纳：bge-m3（~2.3GB）+ bge-reranker-v2-m3（~2.3GB）+ 推理激活（batch 8 × 512 tokens）≈ 5GB+，实测无 OOM。要点：
- 两个模型都 `lru_cache` 单例，绝不重复加载
- reranker `max_length=512`（查询+块 拼接后够用），batch 适配显存
- 服务启动时在 FastAPI lifespan 里**预加载全部模型**，避免首次请求卡半分钟

## 面试高频问题

**Q: 混合检索一定比纯向量好吗？**
A: 不一定，看查询分布。纯语义改述类查询（"机器人的'大脑'指什么"）BM25 贡献有限甚至引入噪声——所以融合后必须有 rerank 兜底把噪声排下去。三件套（双路+RRF+rerank）是作为整体生效的，单加 BM25 不加 rerank 收益可能为负。

**Q: rerank 这么准，为什么不直接用它检索全库？**
A: 计算量。1万块每查询要1万次模型前向，秒级×万=不可用。两阶段的本质是**用便宜的方法把候选从1万降到30，再用贵的方法精挑**——计算预算的分配问题。

**Q: RRF 的 k 怎么调？**
A: k 越小头部权重越大（rank1 优势明显），越大越平均。60 是原论文经验值，对 top15 的召回深度不敏感，一般不动。真要调，应该建评估集看 NDCG/MRR，而不是拍脑袋——这也是下一步做 RAGAS 评估体系的动机。

**Q: 为什么选 bge-reranker-v2-m3 而不是 LLM 直接打分？**
A: 专用 reranker 是为排序训练的判别模型：快（30候选1秒）、便宜（本地推理）、分数稳定可比。用 LLM 逐对打分慢且贵，分数还不稳定（同输入不同次打分会漂）。LLM-as-judge 适合离线评估，在线精排用专用模型。
