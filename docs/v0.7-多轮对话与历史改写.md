# v0.7 多轮对话与历史感知查询改写

> 一句话：让系统能接住追问。先问"宇树机器人的发展历程"，再问"它的融资情况呢"——系统结合上文把"它"还原成"宇树科技"，再走原有检索链路，召回和回答都精准锁定宇树融资。

## 为什么这一期重要

在此之前每个问题都是独立的，任何代词追问（"它/这两家/那再详细说说"）都会答歪——因为检索拿到的是字面追问，无法解析指代。一个对话式产品不支持追问，是用户一上手就会撞到的硬伤。

关键认知：**只加 checkpointer（存历史）并不能让检索变好**。如果只是把历史塞进生成 prompt，会出现"答案像在对话、但检索还是按原始追问跑、召回错"的割裂。真正让追问可用的是**检索前的历史感知改写（condense question）**——把追问重写成不依赖上下文的独立问题，再喂给检索。

## 技术方案

在原 LangGraph 图最前面插一个 `condense` 节点，并用 checkpointer 按 `thread_id` 跨轮保存历史：

```
START → condense（历史改写+重置瞬态）→ route → ...（原检索链路）... → synthesize → END
                                                                          ↓
                                              history += [用户原问, 本轮回答]（add_messages）
compile(checkpointer=MemorySaver())   每次 invoke 带 config={"configurable":{"thread_id":...}}
```

### 1. condense 节点：把追问改写成独立问题

```
根据对话历史，把最新问题改写成不依赖上下文、可独立检索的完整问题：
- 把"它/这个/该公司/上面提到的"等指代替换为历史中的具体实体
- 补全省略的主语/对象
- 若已完整或与历史无关则原样输出
```

- **首轮零开销**：没有历史时直接返回原问题，不调用 LLM，首问不增加任何延迟；只有追问才付一次 fast 档调用。
- 改写后的 `standalone_question` 贯穿下游：路由判断、子查询拆解、混合召回、reranker 精排、最终合成**全部用它**，原始问题只用于回显和写入历史。
- 前端把改写结果作为一个推理步骤回显——"结合上文，理解为：宇树机器人的融资情况"，让用户看见系统"听懂了"。

### 2. checkpointer 与历史

- `MemorySaver`（进程内，按 thread_id 隔离）：单用户演示足够，多标签页天然隔离，无新增依赖。要跨重启持久化换 `SqliteSaver` 即可，上层零改动。
- 历史里存**用户实际问的原话** + 本轮回答（回答截断到 200 字喂给下一轮 condense），用 `add_messages` reducer 自动累积；condense 只回看最近 3 轮，控制 prompt 体积。

### 3. 踩的坑：跨轮状态污染

checkpointer 会持久化**整个** state。上一轮残留的 `retried=True`、`sub_queries=[...]` 会泄漏到下一轮——导致这一轮的简单问题误用上一轮的子查询、或自修正重试被错误抑制。
→ 解法：`condense` 作为每轮第一个节点，顺手把瞬态字段重置（`retried=False`、`sub_queries=[]`）；只有 `history` 用 reducer 累积、其余字段每轮被各节点覆盖。

### 4. 前端：会话与新对话

- 每个页面会话生成一个 `thread_id`（`t-时间戳-随机`），每次 `/ask` 携带；刷新页面或点"新对话"即换新 id、清空消息、隔离上下文。
- 流式事件复用：condense 节点的 update 到达时回显"理解为…"并据改写后的问题召回图表，token 流仍只取 synthesize 节点。

## 实测效果

| 轮次 | 用户输入 | condense 改写 | 召回/回答 |
|---|---|---|---|
| 1 | 宇树机器人的发展历程 | （首轮，原样） | 发展时间轴 + 各阶段 |
| 2 | 它的融资情况呢 | **宇树机器人的融资情况** | 宇树C轮、投后估值超100亿、腾讯/阿里/蚂蚁/吉利等 |

代词"它"被正确还原，检索与答案精准锁定宇树融资，图表召回也跟着用改写后的问题。

## 面试高频问题

**Q: 为什么不直接把历史拼进生成 prompt，省掉 condense？**
A: 那样只有"答案"知道上下文，"检索"仍按字面追问跑——"它的融资"会去检索字面，召回错，答案再流畅也是无源之水。RAG 的瓶颈在检索质量，所以必须在**检索前**做指代消解。这也是 LangChain `create_history_aware_retriever` 的同一思路。

**Q: condense 多调一次 LLM，延迟和成本怎么控制？**
A: 首轮（无历史）完全跳过，零开销；追问才付一次 fast 档（最便宜模型）调用，且与后续路由共用一档。历史只回看最近 3 轮、回答截断 200 字，prompt 体积可控。

**Q: 改写错了怎么办？**
A: prompt 明确"已完整或无关就原样输出"，避免过度改写；前端回显改写结果，用户能立刻看出是否被带偏；最坏情况退化为"按原问题检索"，不比改造前更差。

**Q: 为什么用 MemorySaver 而不是持久化存储？**
A: 单用户演示场景，对话本就不需要跨服务重启存活，thread_id 也是按浏览器会话生成的。架构上换 SqliteSaver/Postgres 只是一行 compile 参数，上层无感——和向量库抽象层一样，先用最简实现打通，留好替换接口。
